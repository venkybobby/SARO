Change Debrief — STORY-TAB-001..007
Seven /app tabs that rendered improper values, fixed as a stacked chain (PRs #128–#134)

Context — why this exists

A review of the deployed UI (sarofrontend.fly.dev/app) found seven tabs showing wrong or empty values. The root cause was not missing data: the frontend and backend had been written against imagined versions of each other's contracts. Pages read response keys the API never returns (d.items vs {traces}), called endpoints that don't exist, hardcoded step lists the backend replaced, and — worst for a compliance product — two backends emitted fabricated values (hardcoded risk tiers, lifecycle stages, framework coverage) that rendered as recorded facts on evidence surfaces.

Each fix treats the backend contract as canonical, pins it with a red-first test, and logs a finding (FND-073..083) so a revert can never merge silently once vitest runs in CI (FND-074, in progress).

Quiz — check your understanding

1. Why did the Remediation tab show "all findings addressed" even for tenants with open failures?

It read d.items from a response shaped {traces, total, …} — the key never existed, so the list was always empty and the empty-state (an implicit all-clear) always rendered. The data was there; the binding wasn't.

2. Why does Mark Complete now demand a note before sending anything?

The canonical endpoint 422s on a blank remediation_note — the note is the human-in-the-loop audit evidence (an AuditEvent is written server-side). Sending without one would always fail; collecting it preserves SARO's HITL posture.

3. What breaks if someone re-adds lifecycle_stage: "production" as a default in the AIMS response?

test_no_fabricated_classification_fields fails (asserts the key is absent), and the frontend pin fails on any default badge (regex covers all five stage words). Conceptually: a fabricated classification would again render as recorded fact on an ISO 42001 evidence surface — Non-Negotiable 4 territory.

4. Why was the Evaluations fix a one-word backend change instead of granting the compliance_lead persona access?

Least privilege: personas are a display/navigation axis; the backend gates on account roles. Widening to a persona would let any role wearing that persona read global QA runs. Instead admin (a super_admin-provisioned role whose nav already showed the tab) joined the read-only list gate, and compliance_lead lost the dead nav entry.

5. Why does the Drift Alerts "no drift" state now show a timestamp?

An unverifiable green claim is the FND-030 class (unbacked "verified" banner). Rendering checked_at makes the reassurance evidently a fresh computation, not static copy.

6. Why does the Rule Packs list still NOT include rules inline — isn't that the bug?

No: the list is deliberately light (rule_count only) and that asymmetry is now pinned. The bug was that nothing ever fetched the per-pack detail. Master/detail keeps the list cheap while the detail endpoint serves the full rules array.

7. What made all four CI jobs fail on PR #128 when everything was green locally?

One root cause, two gates: (a) CI installs unpinned ruff, and a new release added rules → 1491 errors in pre-existing files, which also tripped the quality ratchet's ruff-count; (b) the lifecycle guard demanded the verify-stage debrief this document satisfies. Neither failure was caused by the diff under test — the FND-069 lesson repeating.

8. If the onboarding backend adds a fifth step next quarter, what frontend work is needed?

None — both surfaces render the API's steps array data-driven (label + completed). Only an optional entry in ONBOARDING_STEP_NAV if the new step deserves an in-app Go button; unknown keys already render label-only (pinned by the "unknown future step keys" test).
