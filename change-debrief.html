STORY-DISP-001 — Finding Disposition Lifecycle

Change debrief · story 6/8 · shelfware-risk P1 · stacked on story/STORY-META-001

1. Context

A failed evaluation used to terminate at the finding — there was no acknowledge/remediate/waive lifecycle (the notifications table had 0 rows). An examiner asking "you found this problem; what did you do about it?" had no answer. DISP-001 makes every failed finding enter a tracked disposition lifecycle, because dispositions ARE evidence.

2. Intuition — the state machine

Forward-only, each hop stamped actor+timestamp and sealed into a per-disposition SHA-256 transition log (append-only, trigger-immutable). An expired WAIVED auto-reopens to OPEN — the one backward edge, system-driven — and fires the first real notifications row. De-identified throughout (INV-2): rule/gate/system ids and severity, never observed content.

5. Understanding check

Why does a recurring finding link to the prior disposition instead of creating a new one?
create_disposition checks for an ACTIVE disposition with the same (tenant, rule_id, system_id); if found it increments recurrence_count and returns it. Otherwise a re-failing check would spawn unbounded duplicate rows for one underlying problem, drowning the report. Recurrence under an active waiver does NOT auto-escalate in v1 (recorded, not acted on).
How is the expired-waiver reopen a "lineage reference to the expired waiver" if it's the same row?
The append-only transition log holds the lineage: the row gets a new WAIVED → OPEN transition with reason "waiver expired {date}", so the full history (opened → acknowledged → waived → reopened) is sealed and verifiable. The waiver fields remain on the row, and the report surfaces the reopened-waiver lineage. No duplicate disposition is created.
Why is bulk-waive forbidden while bulk-acknowledge is allowed?
A waiver is an accountable risk-acceptance decision that requires its own justification, approver, and expiry — batching them would let someone rubber-stamp many risk acceptances with one rationale. Acknowledgement is just "I've seen this", so batching it is safe. There is simply no bulk-waive endpoint.
The TEN-001 test failed when this story added a table. Was that a bug?
No — it was the schema-completeness guard working exactly as intended. Adding dispositions (a tenant_id-bearing table) without registering it tripped test_every_tenant_scoped_model_is_accounted_for, forcing this story to add the RLS policy (migration 034) and update the isolation inventory. That's how AC-1's "no tenant table relies on zero policies" stays enforced over time.
