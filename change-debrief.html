STORY-RPV-001 — Versioned, Immutable Rule-Pack Snapshots

Change debrief · foundation story of the RPV/CHUB/TEN/META/DISP/MTR/COV batch · branch story/STORY-RPV-001

1. Context — why this exists

On 2026-07-04 a "regulatory radar" session mutated rule rows in place in the live tables (eu_ai_act_rules, governance_rules). The problem: a historical attestation says "this output was evaluated against the rules" — but the rule text has since changed, and SARO keeps zero payload content, so you cannot re-run the evaluation to see what it actually checked. An examiner asking "which rule version did this attestation use?" had no answer.

RPV-001 fixes the criteria side of evidence integrity: it lets you freeze the rule tables into an immutable, hash-identified version. RPV-002 (next) pins each attestation to one of these versions, closing the loop. This story builds the snapshot mechanism; it deliberately reuses the proven EVF hash-chain pattern rather than inventing new cryptography.

2. Intuition — the mental model

Think of the three rule tables as a working copy (a git working tree). Publishing is git commit: it freezes exactly which rows, at what content, were in force — and links to the prior commit by hash. Each snapshot stores a manifest of per-row hashes (not the full rule text) plus a content_hash over all included rows, and a record_hash that chains to the previous version. Tampering with any snapshot breaks the chain from that version forward — detectable by walking from genesis.

6. Understanding check

Why store per-row hashes in the manifest instead of the full rule text?
Avoids duplicating the entire rule corpus into every snapshot row (table bloat), while still being tamper-evident: content_hash covers every included row's canonical serialization, so any later edit to a working-copy row changes its hash and is caught by diff. The full text is reconstructable from the working tables + diff. RPV-002's criteria-reproduction will read the pinned version's rows.
Why is immutability enforced in two places, and which one do the unit tests exercise?
The SQLite test harness can't run plpgsql triggers, so the DB trigger (defense-in-depth on real Postgres) is unit-untestable there. The service-layer guard is what the unit tests hit (update_snapshot_version always raises SnapshotImmutableError); the trigger was verified separately against live Supabase. This mirrors the existing EVF split (app-enforced QCO + trigger-enforced publication events).
A DRAFT_UNVALIDATED row exists in eu_ai_act_rules. What happens on publish, and why is that the safe default?
Publish is refused with a listing of the blocking (table,id) rows (HTTP 409). You cannot freeze a version while unvalidated draft rules float in it — a published snapshot is examiner-facing and must contain only SME-validated (or explicitly-caveated legacy) content. NULL status is treated as DRAFT (fail-closed), so a future insert bypassing the default can't silently enter a snapshot.
What breaks if the canonical serialization used json.dumps(payload) without sort_keys=True?
Row hashes would depend on dict insertion order, so the same row could hash two different ways across Python versions/runs — producing spurious "tamper" verdicts and unstable content_hash values (empty-publish detection and the chain would both misfire). Deterministic, sorted, UTF-8 canonical form is the whole basis of the tamper-evidence claim.
Why does NIST (nist_ai_rmf_controls) get treated as LEGACY rather than blocking like a NULL status?
NIST has no validation_status column at all (the radar migration only touched EU + governance). "Column absent" is a different fact from "column present but NULL": absent → the table has no lifecycle yet → LEGACY (includable-with-caveat under the flag); present-but-NULL → a row that should have a status but doesn't → fail-closed as DRAFT. The service distinguishes these via the has_status flag in _RULE_TABLES.
How does RPV-001 preserve SARO's "never calls external models / evidence-only" posture?
Everything is local: SHA-256 over rows already in the DB, no network calls, no model inference, no writes to client systems. The endpoints return hashes, counts, and diffs — evidence artifacts for a human auditor, never a compliance verdict. The publish action is an internal admin operation on SARO's own reference data.
