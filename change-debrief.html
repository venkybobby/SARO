STORY-412 — Demo surface trim: every visible tab must survive a click

Ownership review demo-readiness pack — P0 blocker #2. Paired with the UC-5 manifest reconciliation and FND-051 (incidental).

Context — why this exists

The public /demo route is the AI-Auditor persona's first (and often only) look at SARO. A prospect who clicks one thing off the happy path and hits a blank screen or a 403 reads as "this product is half-built" — regardless of how good the core scoring is. The story's own framing: "the demo must show fewer things that all work, not more things that mostly work."

Investigating the stated premise ("Sidebar renders the compliance_lead tab set, causing 403s") turned up something worse: the demo route had no navigation at all. DemoEntry.jsx rendered a bare Dashboard component with onNavigate left undefined — every quick-action button was a silent no-op. There was nothing to 403 on because there was nothing to click.

Intuition — before / after

Mental model: AppShell (Sidebar + page router) used to live only inside the authenticated /app route, defined inline in App.jsx. It's now a standalone component both the authenticated route and the public demo route render — the demo session is just "AppShell with a synthetic role=demo_viewer user," not a special-cased second UI.

Quiz

Q1. Why does DemoEntry.jsx need to render AppShell instead of just adding an onNavigate handler to the standalone Dashboard?
Because the story's whole premise — a Sidebar with a DEMO_TABS whitelist — requires Sidebar to actually be rendered. AppShell is the only place Sidebar mounts; without it there's no navigation surface to trim in the first place.
Q2. If you deleted the persona_role: "compliance_lead" line from routers/demo.py, would any endpoint start returning 403 for the demo token?
No. auth.py's get_current_user hardcodes persona_role="compliance_lead" server-side for any role="demo_viewer" token regardless of the JWT's own claim — confirmed independently by the security-auditor. The line is there for claim/behavior consistency, not access.
Q3. Why is demoTabs.json a separate file instead of a constant inside Sidebar.jsx?
AC-1 requires the frontend whitelist and the backend contract test to read from one shared source so they can't drift apart — Python can't import a .jsx module, but both can load a JSON file.
Q4. What would break if FND-051's router swap had gone the other way (evf_sprint2 after evf_sprint3, but evf_sprint3 also had a generic path)?
It would just move the shadowing bug rather than fix it. This wasn't the case here — evf_sprint3 has no generic /qco/{...} pattern, confirmed by reading its full route list before swapping, and pinned by a test asserting the generic route still resolves post-swap.
Q5. A demo visitor opens devtools and manually sets activePage to "upload" in React state. What stops them from reaching the real Upload page?
Nothing client-side — DEMO_TABS is a UI convenience, not a security boundary. The real control is that every backend endpoint keeps its own auth dependency (require_role, require_write_access, etc.); a client-side bypass would render the Upload page's chrome but every write it attempts still 403s server-side.
Q6. Why does the AC-4 test PUT to /compliance/readiness/{key} in addition to POST /ingest?
/ingest is gated by role (demo_viewer was never in its allowlist) — a weaker test of read_only enforcement specifically. The readiness toggle is the one write button an actual DEMO_TABS page renders, and its gate (require_write_persona) checks read_only first — a more direct regression pin for what a demo visitor could try to click.
