Task: "Run Playwright and create the end-to-end flow for the use cases planned for Demo" against sarofrontend.fly.dev / saro-backend.fly.dev · 2026-07-22

1 · Context — why this exists

The demo readiness review (2026-07-19) found the CI "E2E Smoke Tests" job was vacuous: all 13 @pytest.mark.e2e tests were pass placeholders, so no real browser ever loaded the demo pages before an attendee did (finding F3 — the structural gap that let the "1286/100" badge and the red "API offline" dot ship). The pre-demo checklist RB-006 existed only as manual curl blocks. This change turns RB-006 §§A–E and §H into one command:

SARO_LIVE_E2E=1 pytest tests/e2e -m e2e -q

The demo itself runs on the public /demo flow and shows five planned use cases from scripts/demo_manifest.yaml: UC-1 PHI leakage, UC-2 hallucinated clinical guidance, UC-3 missing disclaimer, UC-4 prompt-injection echo, UC-5 unapproved model (→ ENV-MODEL-ALLOWLIST-1). UC-1/2/5 are expected to fire; UC-3/4 are planted-pending-rule.

2 · Intuition — before / after

Mental model: the suite is a deployment gate, not a unit test. It asserts the demo-ready state of the live system; when the system isn't demo-ready, the correct output is a red test whose message quotes the runbook remedy. That is exactly what happened on the first run.

7 · Quiz — do you actually hold the model?

1. Why does the suite skip unless SARO_LIVE_E2E=1 instead of just being marked e2e?

Because CI runs pytest tests/ -m e2e on every PR with no deployment in scope. Unarmed, these tests would either fail CI whenever fly.dev is unreachable or force every PR to depend on prod state. The env-var arm makes "hermetic CI" and "live pre-demo gate" two modes of one suite.

2. All five failures today have one root cause. What is it, and what's the remedy?

The live demo tenant has zero audits — the STORY-407 corpus was never ingested (or was reset). Remedy per RB-006 §C: python cli.py demo reset --tenant <id> --yes then re-ingest; re-run the gate and expect 23/23.

3. Why are UC-3 and UC-4 not asserted as findings when they're planned demo use cases?

demo_manifest.yaml marks them expected: planted_pending_rule — the rules (missing-disclaimer, RP-INJ-BOUNDARY) don't exist yet. Asserting findings for them would encode a phantom implementation (failure mode FM-1/FM-2).

4. What breaks if someone reseeds with the pre-FND-059 seeder?

Stored overall_risk_score would be 0–100 instead of 0–1; the frontend multiplies by 100 once, so badges read "1286/100". test_c_risk_scores_are_probabilities fails on any stored score > 1.0 — catching the F1 blocker before an attendee sees it.

5. Why does the browser flow enter at /demo and never /app?

/app requires interactive login credentials; /demo mints a public read-only JWT via GET /api/v1/demo/token and renders the trimmed DEMO_TABS shell — which is exactly the surface the planned demo uses (RB-006 §H).

6. What would a 2xx from test_e_demo_token_cannot_ingest mean?

That the PUBLIC demo token can write to SARO — anyone on the internet could ingest data into the demo tenant. RB-006's words: "stop everything and fix." It also violates non-negotiables #3/#6.

7. Why watch network responses during the tab walk instead of just checking pages render?

A React page can render its chrome while every data fetch 403s/500s underneath. The ≥400 watch is the automated version of "DevTools Network open, zero red rows" — it catches whitelist violations and 500s that the DOM hides behind empty states.

8. What does the hard-refresh test actually pin, beyond "the page loads again"?

Two invariants: DemoEntry re-mints the token cleanly (the demo doesn't die on an accidental F5 mid-pitch), and the JWT never lands in localStorage — it's React-state-held, so a shared/kiosk machine doesn't retain a token after the tab closes.

9. If CI's STORY-412 census test is green but §B fails live, what does that tell you?

The deployed build is behind main (CI pins the census against the in-process app; this suite pins it against the deployment). The failure message says exactly that — deploy, don't debug.
