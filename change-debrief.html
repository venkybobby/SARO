STORY-META-001 — SARO Self-Audit: Governance of the Governance Tool

Change debrief · story 5/8 · SOC 2 spine · stacked on story/STORY-TEN-001

1. Context

SARO audits its customers' AI, but its own audit_events table was empty — who viewed evidence, changed rules, or exported what was unanswerable. The 2026-07-04 out-of-band rule mutation would have shown up here, and didn't. META-001 makes SARO survive the scrutiny it applies to others: an immutable, hash-chained trail of privileged actions, plus DB-level capture of out-of-band writes so the API isn't the only thing watched.

2. Intuition

Two chains, one table. App-layer events (RULE_PACK_CHANGE, EVIDENCE_ACCESS, EXPORT…) are sealed into a per-tenant SHA-256 chain (reusing the evidence-store discipline) — content-free, metadata only. Out-of-band writes to the rule tables are caught by a statement-level DB trigger that appends a RULE_PACK_CHANGE with actor=db:role, honestly flagged as outside the app chain. Global actions (rule-pack changes aren't tenant-specific) live on a dedicated SYSTEM tenant chain.

6. Understanding check

Why does EVIDENCE_ACCESS fail OPEN while a privileged action fails CLOSED?
A read is the customer's compliance function doing its job — blocking it because SARO's self-audit hiccuped would harm availability for a benefit (self-audit completeness) that matters less in that moment. A privileged WRITE that can't be audited is exactly what you must not let happen silently, so it fails closed (aborts). The tradeoff is documented, not accidental.
Why do out-of-band (DB-trigger) and backfill events sit OUTSIDE the hash chain?
The app-layer chain seals events the service creates in order. A DB trigger firing on a raw SQL write can't compute the Python canonical hash, and backfill events predate the chain entirely. Rather than fake a chain link, they're captured with seq=NULL and honestly flagged (out_of_band / retroactive) — queryable, but excluded from verify_audit_chain. Honesty over a fake-complete chain.
Why does the SYSTEM tenant UUID start with 'a'?
An all-numeric UUID string (once dashes are stripped) is a valid number, and SQLite's NUMERIC type affinity coerces it to an integer on readback in the test harness — so uuid.UUID(1) blows up. A leading hex letter keeps it TEXT. Real Postgres UUID columns are unaffected; this is purely a test-harness robustness choice.
How is the trail content-free, and why does it matter?
Only metadata is hashed and stored — actor, action class, target id, outcome, timestamp — never the prompt/output/evidence content. An audit log that copied evidence content would itself become a PII-retention liability (INV-2/INV-3), turning the compliance feature into a compliance risk. The metadata passed at call sites is hashes/counts only.
