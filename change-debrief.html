STORY-RPV-002 — Attestation Evidence Pins Rule-Pack Version

Change debrief · story 2/8 · stacked on story/STORY-RPV-001

1. Context

RPV-001 made rule-pack versions immutable. But an attestation's evidence record didn't say which version it was evaluated against — and SARO keeps zero payload content, so you cannot re-run the evaluation. RPV-002 stamps every evidence record with the rule-pack version + content hash in force, inside the record's own tamper-evident hash chain. That pin is the only link between an attestation and its criteria. It also lets you reproduce the exact frozen rule text on demand — the examiner question "which rule version did this attestation use?" now has a provable answer.

2. Intuition

Discovery: the GRC checks evaluate against a static versioned crosswalk (framework_crosswalk.json), not the live DB rule tables — so "working-copy rules must never be the evaluation basis" (AC-2) was already structurally true. The pin is therefore a provenance annotation + an evaluation gate, not a check-logic rewrite.

6. Understanding check

Why does adding two fields to _PAYLOAD_FIELDS not corrupt existing evidence records?
The content hash is recomputed from the same _PAYLOAD_FIELDS on both write and verify. Existing rows get the two new fields as NULL (migration default), and verify reads them the same way — so the chain stays self-consistent. New captures include the resolved pin. Nothing rehashes historical rows behind the scenes; PRE-VERSIONING rows simply carry a NULL pin.
PERMISSIVE mode, no snapshot published yet. What gets pinned, and does evaluation proceed?
resolve_pinned_version returns (None, None); the record is stamped PRE-VERSIONING and evaluation proceeds. STRICT mode instead refuses. This is the honest-gap posture: an unpinned record is explicitly labelled, never faked.
The working copy changed after v1.0.0 was published. What does /versions/1.0.0/reproduce return?
The frozen rule text stored in snapshot_content at publish time — not the mutated live rows. That is the whole point: reproduction must survive working-copy mutation, since the pin is the only link to the criteria of record.
Why resolve the version at capture time rather than at audit time?
AC-1 puts the pin on the evidence record when it is persisted, and the pin must be inside that record's content hash. Capture is where the record (and its hash) is created, so resolving there makes the pin tamper-evident in the same chain. The audit reads the pinned version off the record.
How is a cross-tenant criteria read prevented?
get_evidence filters on tenant_id, and the endpoint passes the caller's current_user.tenant_id; a foreign or nonexistent id both yield a generic 404 (no existence oracle). The reproduced rule content is global reference data with no tenant/PII fields.
