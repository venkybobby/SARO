Signed Jira OAuth State — TM-F1 fix debrief

security: OAuth CSRF FND-061 pinned FND-062 pinned FND-063 open auditor: PASS-WITH-FINDINGS (fixed in-PR) reviewer: APPROVE

Context — why this exists

SARO can file Jira tickets for audit findings. To do that, a tenant connects their Jira Cloud account through OAuth: SARO sends the user to Atlassian, Atlassian redirects back to SARO's callback URL with a one-time code, and SARO trades that code for access tokens which it encrypts and stores for the tenant.

The problem (threat-model finding TM-F1): the callback identified the tenant purely from a state query parameter that anyone could set to any tenant's UUID. The callback is necessarily unauthenticated (it's a browser redirect from Atlassian), so nothing stopped an attacker from completing a forged callback: authorize their own Jira account, then hit SARO's callback with their code and a victim tenant's UUID as state. The victim tenant's Jira integration would silently become the attacker's Jira account — every subsequent "create issue" would leak finding details to the attacker. This is the textbook OAuth CSRF the state parameter exists to prevent.

Intuition — the mental model

Think of state as a claim ticket. Before, SARO accepted a claim ticket that anyone could write themselves ("this coat belongs to tenant X"). Now the ticket is printed by SARO on tamper-evident paper: it contains the tenant id, an issue timestamp, and a random nonce, all covered by an HMAC-SHA256 signature only SARO can produce. And SARO keeps a stub (the nonce, on the tenant's row) — the ticket is honored once, within 10 minutes, and the stub is destroyed before the coat is handed over.

Logged deviations

FND-062 storage move. The callback wrote tokens to ClientConfig.settings_json — a column that does not exist on that model, so the write raised AttributeError, was swallowed by a broad except, and the endpoint returned 200 anyway. Token persistence (write and the create_jira_issue read) moved to Tenant.settings_json, which exists. The aggressive alternative (a migration adding the column) was rejected as larger blast radius.
Finding IDs renumbered from 058/059/060 to 061/062/063 mid-task: origin/main advanced 4 commits during the work and claimed the original IDs (PR #124). The append-only ledger stays append-only.

What was deliberately NOT done

  • No role gate on /oauth/jira/start — any authenticated tenant user can still (re)bind the tenant's Jira connection. Pre-existing posture, logged as FND-063 (open) per the auditor's own recommendation rather than silently widening this diff.
  • No async httpx.AsyncClient conversion — the sync httpx.post in an async handler predates this change and matches the file's (already-ledgered, FND-024-class) pattern.
  • No per-nonce multi-flow support — one pending OAuth flow per tenant (second /start overwrites the first). Adequate for the integration's usage; noted under FND-063.
  • No migration — deliberately zero schema change.

Quiz — do you actually hold the model?

1. Why does the callback have to trust state at all — why can't it just use the logged-in user's tenant?
The callback is a browser redirect from Atlassian, not an authenticated API call — there is no SARO session or JWT on that request. The tenant identity must ride inside the redirect itself, which is exactly why it must be integrity-protected.
2. The HMAC signature already proves SARO minted the state. Why is the nonce still necessary?
A signature verifies forever — a leaked or intercepted state would stay valid for its whole TTL, replayable any number of times. The nonce, stored server-side and destroyed on first use, adds the one property signatures can't give: single use.
3. Why is the nonce consumed before the token exchange instead of after success?
If it were consumed only on success, a callback that fails mid-exchange would leave the nonce alive — and a captured state could be replayed against the token endpoint. Consuming first means a replay can never cause egress; the worst case is the legitimate user restarting the flow.
4. What breaks if the timestamp were outside the HMAC'd payload?
An attacker could take a validly signed state and swap in a fresh timestamp forever, defeating the TTL. Every field an attacker could benefit from altering — tenant, time, nonce — must be under the MAC.
5. Why compare signatures with hmac.compare_digest on bytes, and not == on strings?
Two reasons: == short-circuits at the first differing byte, leaking timing information an attacker can use to forge a signature byte-by-byte; and str-mode compare_digest raises TypeError on non-ASCII input, turning attacker garbage into a 500 instead of a clean 400.
6. What would have happened if we'd "fixed" TM-F1 but left token storage on ClientConfig.settings_json?
The CSRF fix would have been untestable theater: the happy-path test asserts the decrypt round-trip on the stored tokens, and that write silently never persisted (nonexistent column, swallowed AttributeError). Binding tokens securely to a tenant is meaningless if the binding is never written.
7. Why does a missing signing secret return 500 rather than falling back to a built-in default key?
A known default key means anyone can mint valid states — TM-F1 reintroduced with extra steps. This repo has already ledgered exactly that bug class (FND-044, the EXPORT_HMAC_SECRET hardcoded default). Fail-closed is the only safe behavior.
8. What attack does with_for_update() close, and why can't our test suite prove it?
Two concurrent callbacks carrying the same state could both read the pending nonce before either commits the delete — both "spend" it once (TOCTOU race). The row lock serializes verify-and-consume on Postgres. The test harness runs SQLite, where FOR UPDATE is a no-op, so this is verified by code review, not by a pinning test.
9. An attacker steals a victim's unexpired, unused state value. What can they do with it?
Race the victim: whoever reaches the callback first consumes the nonce. If the attacker wins with their own authorization code, they bind their Jira account to the victim tenant — which is why state values must be treated as secrets in transit (TTL + single-use bound the window; FND-063's role gate would further limit who can mint them).
10. Why 400 for every rejection reason rather than distinguishing "expired" from "bad signature" in the response?
Distinct responses give an attacker an oracle to probe the verifier one property at a time (e.g. confirm a signature is valid but expired). The reason category goes to server logs for defenders; the caller gets one uniform answer.
