STORY-408 — Cross-Account Client Log Pull

Verify-stage debrief. Spec: specs/stories/STORY-408.md. Full history in implementation-notes.md.

Context

SARO's ingest pipeline only ever authenticated with SARO's own AWS credentials against SARO's own S3 bucket — fine for the demo corpus, useless for a real client. A real client's Bedrock invocation logs live in their account, in their bucket, usually SSE-KMS encrypted. Clients will not push logs to us (wrong trust direction); SARO has to pull by assuming a client-provisioned, read-only, least-privilege IAM role. This story builds that machinery: the per-tenant config that remembers which role/bucket/prefix belongs to which tenant, the STS AssumeRole + credential-refresh plumbing, the security properties that make "SARO reads your bucket" safe to hand a security reviewer, and the CloudFormation template + one-pager a client engineer runs to grant access in minutes.

Pilot-gated per the spec header — the owner explicitly instructed building ahead of the SummitCare pilot signature (Decision Log Q2), with every live-AWS-only verification item flagged open rather than silently assumed.

Intuition — before / after

The one-sentence mental model: every read is now scoped to a role the client themselves granted, for exactly one bucket/prefix, with credentials that expire and auto-refresh — SARO's own credentials never touch a client's bucket.

Quiz — test your understanding

Click a question to reveal the answer. This checks the mental model, not filenames.

1. Why generate a per-tenant external_id at all if the IAM trust policy already restricts the principal to SARO's AWS account?
The account-level trust restricts who can attempt AssumeRole (any principal in SARO's account), but not which tenant's role SARO's shared codebase might accidentally assume. external_id is the confused-deputy defense: SARO generates a random one per tenant, the client's trust policy requires it, and it never leaves SARO's control as an AWS credential — it's a shared secret proving "this specific tenant's pull is the one authorized," not an authentication mechanism AWS itself trusts blindly.
2. What would break if refreshable_session re-assumed the role per-batch instead of using botocore's RefreshableCredentials?
Nothing would break functionally — it was the explicitly considered alternative (Decision Log Q4) — but every call site (replay_backfill, the CLI) would need new re-assumption checkpoints threaded through the ingest loop. The refreshable-credentials approach makes the S3 client itself transparently refresh under the hood, so zero new orchestration code is needed anywhere credentials are used.
3. Why derive account_id from role_arn instead of storing it as its own column on TenantLogSourceConfig?
An IAM role ARN already embeds its account id (arn:aws:iam::<account_id>:role/...). Storing a second copy creates a place for the two to silently drift — e.g. an operator updates role_arn but forgets the separate account_id field, and the Bedrock S3 key-layout prefix (AWSLogs/{account_id}/...) starts looking in the wrong place with no error.
4. What breaks if _validate_key_shape were removed from S3LogStore.read_bytes but kept in LocalLogStore.read_bytes?
S3 itself has no real directory-traversal vulnerability (keys are opaque strings, not filesystem paths), so nothing would be exploitable today. But it would mean the cross-account S3 path no longer has the same defense-in-depth as the local path against a malformed/hand-edited key reaching a GetObject call outside the intended shape — and would break the symmetry the security review relies on ("both paths get the same check").
5. Why does the KMS error handler name the specific key ARN instead of just re-raising AWS's generic AccessDenied?
A missing kms:Decrypt grant on the client's log-encryption key is called out in the story as "the #1 client setup mistake" — a generic AccessDenied gives a client's cloud engineer no idea what to fix. Naming the exact key ARN turns a support escalation into a one-line IAM policy fix.
6. What's the actual gap in AC-3.1's test coverage, and why can't a moto-based test close it?
AC-3.1 wants proof that assuming the role without the correct external_id fails. moto simulates the AWS API surface but does not simulate IAM trust-policy evaluation — its fake AssumeRole accepts any ExternalId. So the test can only prove SARO's code always sends the correct external_id (necessary but not sufficient); proving AWS actually rejects a wrong one requires a real AWS account with a real trust policy, which is exactly why this is folded into the pre-pilot live-AWS verification pass rather than claimed done.
7. What actually happens if an operator runs saro ingest --tenant X --account-id 999999999999 when tenant X's real config points at a different account?
No security boundary breaks — allowed_s3_buckets and the S3 client itself stay pinned to tenant X's real resolved bucket/role, regardless of the flag. But object discovery uses AWSLogs/{account_id}/BedrockModelInvocationLogs/{region}/... as the key prefix, so the wrong account-id silently produces a prefix that doesn't match any real objects — the run "succeeds" with zero objects discovered, no error. That's FND-055.
8. Why does ValidatedSourceConfig (the service-layer dataclass) override __repr__/__str__ to redact external_id, but the ORM model TenantLogSourceConfig doesn't?
ValidatedSourceConfig is the object actually threaded through CLI code, logged in labels, and passed around at runtime — exactly where an accidental print()/log of the object would leak external_id (AC-1.2 says "never logged"). The ORM model is typically only ever queried by field (row.external_id), not printed wholesale — but this is a thinner guarantee than the dataclass's, worth keeping in mind if a future debug log ever does logger.info(row).
9. Why is the CloudFormation template's kms:Decrypt permission conditional (!If [HasKmsKey, ...]) instead of always granted?
Not every client's Bedrock log bucket is SSE-KMS encrypted — some use SSE-S3 (AWS-managed keys) with no client-controlled KMS key at all. Always including a kms:Decrypt statement would either reference a non-existent key (template fails to deploy) or grant a broader permission than the client actually needs. The conditional keeps the granted policy exactly as narrow as each client's actual setup requires — least privilege applied per-deployment, not just per-template.
10. What's the difference between "AC-3.5's security-auditor gate is satisfied" and "STORY-408 is fully verified"?
AC-3.5 only requires an independent security review before merge — which happened and returned PASS-WITH-FINDINGS (no blocking issues). "Fully verified" would also require the Verification checklist's live-AWS items (a real cross-account pull against a second AWS account, the CloudFormation template deploying clean for real, the onboarding doc's timing actually measured) — all explicitly still open, gated on real AWS access this sandbox doesn't have. The story can be mergeable without being fully verified end-to-end; both facts are recorded honestly rather than one masking the other.
