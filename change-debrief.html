STORY-406 — Bedrock Invocation-Log Adapter

Read-only adapter · backfill audit + observation coverage · PR #112 · branch claude/bedrock-adapter-schema-3lz3yl

1 · Context — why this exists (plain language)

SARO scores AI output it is given; it never calls a model itself. Customers running agents on AWS Bedrock already emit model-invocation logs (to CloudWatch/S3). This adapter reads those logs — after the fact — and feeds them into SARO's two evidence streams:

  • Audit: turn each logged invocation's prompt + response into a scored risk audit.
  • Coverage: emit a heartbeat proving when SARO was observing a system.

migrations/036 and STORY-COV-001 both deferred this "live Bedrock heartbeat" to STORY-406 — this PR is that deferred half, in backfill (historical replay) form. Live-tail is spec'd but follow-on.

2 · Intuition — the one idea that makes it click

The whole design turns on one seam: coverage never touches a message body; audit may. That is SARO's INV-2 invariant (evidence carries positions/timestamps, never observed content). We make it structural, not a promise: emit_coverage() is handed only an Envelope (modelId, cursor, timestamp) — it is physically incapable of reading a prompt. The audit branch is a separate function that resolves bodies (inline, or S3) behind an allowlist-guarded fetch.

6 · Understanding check

Reveal each answer after you've committed to one.

Q1. Why can emit_coverage not leak a prompt, even if a future dev is careless?
Because its signature accepts only an Envelope — a body-free type built by parse_envelope, which reads only envelope keys. There is no message body in scope to leak. INV-2 is enforced by the type boundary, not by discipline.
Q2. What breaks if we used emit_observation instead of record_checkpoint for backfill?
emit_observation overrides the watermark with a time bucket (obs:{floor(ts/bucket)}). Replaying a historical corpus would collapse many distinct records into one bucket and lose resumability. Backfill needs the monotonic cursor as the watermark — that's why the adapter calls record_checkpoint directly.
Q3. Audit idempotency "rides the coverage duplicate signal." What does that require, and what breaks if violated?
It requires do_coverage=True (the backfill default): a re-seen cursor is detected as a duplicate checkpoint, which then skips the re-audit. If you ran do_audit=True, do_coverage=False and replayed twice, you'd duplicate Audit/ScanReport rows and re-run the engine. Documented in code + notes.
Q4. Why is boto3 lazy-imported inside the resolver rather than at module top?
boto3 is an optional dependency (commented out in requirements.txt). Lazy import keeps the parser + coverage branch dependency-free and unit-testable without AWS, and means importing the adapter never pulls boto3. It also keeps S3 reach confined to one function.
Q5. A crafted log record sets inputBodyS3Path: s3://attacker-bucket/secret. What happens?
validate_s3_path rejects it — attacker-bucket is not in the operator's allowed_s3_buckets allowlist (deny-by-default), raising S3PathNotAllowed. The record fails soft (tallied as an audit error); no fetch with SARO's credentials occurs. This is the confused-deputy defense.
Q6. How does the adapter stay clean under the STORY-336 no-external-model guard, given it deals with Bedrock?
It only ever reaches AWS S3 object storage (boto3.client("s3")), never a model-inference endpoint, and contains no bedrock-runtime literal (the guard scans string constants, incl. docstrings). adapters is in the guard's scanned dirs, so this is enforced, not asserted.
Q7. Why does source_model collapse non-Claude Bedrock models to "bedrock" instead of naming each?
D1: widening the enum per model is a maintenance treadmill for zero audit value. The exact model is never lost — it lives in system_id (=modelId) and metadata.modelId. The enum stays a small, stable adapter-family filter; anthropic.*→"claude" still holds.
