Change Debrief — FND-074
The frontend regression tier finally gates CI: vitest (+ eslint) wired into deploy.yml and a new ci.yml job, pinned by a workflow-YAML regression test

Context — why this exists

SARO's enforcement model says a pinned finding is guaranteed by CI: revert the fix and a red gate blocks the merge. That was true for the pytest tier — and silently false for the frontend tier. The ~10 manifest entries pinned by frontend/src/**/*.test.jsx (FND-021/022/023/029/031/052/053/054/073…) ran only on developer machines, because deploy.yml's frontend job did just npm ci + npm run build and ci.yml ran pytest only. A revert of, say, the Remediation contract fix (back to d.items) would have merged and deployed green.

The reviewer logged this during STORY-TAB-001 as FND-074 (status open). This change closes it — and, per the repo's convention for CI-config findings (precedent: FND-084's ruff pin), the pin is a pytest that parses the workflow YAML itself, so deleting the gate turns the backend suite red.

What was deliberately NOT done

  • No --max-warnings 0 on eslint — the tree has 194 warnings today; lint gates on errors only (exit 0 verified). Ratcheting warnings down is separate, deliberate work.
  • No coverage/threshold flags on vitest — the finding is about existence of the gate; adding thresholds would be a born-red or arbitrary bar.
  • No consolidation of the two vitest runs — deploy.yml's frontend job and ci.yml's frontend-test both run on PRs. Owner-specified defense-in-depth (deploy.yml also protects direct pushes to main); costs one duplicate job.
  • No Playwright/E2E frontend tier — out of scope; the E2E smoke job in ci.yml is unchanged.

Quiz — check your understanding

1. Before this change, what happened if a PR reverted Remediation.jsx back to reading d.items?

It merged and deployed green. Remediation.test.jsx would fail — but nothing in CI ever executed vitest; deploy.yml only built the frontend, and a contract-broken page still builds fine. The "pinned" status was a promise only developer machines kept.

2. Why is the pin for a CI-config finding a pytest file rather than a vitest test?

A vitest pin can't guard the vitest gate — deleting the gate also deletes the thing that would complain. The pin must live in a tier that runs regardless: pytest parses the workflow YAML and fails if the vitest step vanishes. Same pattern as FND-084's ruff-version pin.

3. Why does vitest run before npm run build instead of after?

Fail fast and never produce a deployable artifact from a red tree: in deploy.yml the build is the input to flyctl deploy, so tests must gate it, not trail it. The ordering is itself pinned (ci_idx < vitest_idx < build_idx).

4. What breaks if someone moves the frontend-test job's steps out of the frontend working directory?

The pin test fails its working-directory assert. Without it, npx vitest run at repo root would find no vitest install/config and could error — or worse, a future root-level vitest could pass while testing nothing relevant: a vacuously green gate.

5. Why check the key True when asserting ci.yml triggers on pull_request?

PyYAML implements YAML 1.1, where bare on parses as boolean True — so workflow["on"] is a KeyError and the triggers live under workflow[True]. The test checks both, with a comment, so the next reader isn't ambushed.

6. eslint reports 194 warnings — why does the lint gate still pass, and is that acceptable?

eslint . exits 0 unless there are errors (or --max-warnings is set). Wiring it as-is adds a real error gate today without turning 194 pre-existing warnings into a born-red wall for unrelated PRs. Tightening to warnings-clean is a separate ratchet decision.

7. Why did this branch have to be re-based mid-task, and what failure mode did that avoid?

At session start FND-074 didn't exist on origin/main — it landed mid-session when PR #128 merged. Branching off the stale tip and hand-adding the ledger row would have been FM-2 (building on an unverified premise) and guaranteed a conflict. The premise check caught it; the branch was reset to the new tip and the premise re-verified there.
