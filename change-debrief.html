Why this exists

UC-5 in the demo corpus (an off-allowlist Bedrock modelId) was planted since STORY-407 but never fired — SARO's content engine (Gate 3) only ever reads prompt+raw_output text, never the log envelope. "An unapproved model served production traffic" is one of the most visceral governance findings for a healthcare risk officer, and SARO was structurally blind to it. This story gives the engine one narrow new capability: evaluate an envelope attribute (modelId) against a versioned allowlist rule.

The actual root-cause gap wasn't in the engine's capabilities — it was one dropped kwarg. services/audit_submission.py's submit_audit_sync had received metadata (which already carried modelId/requestId, built by the STORY-406 adapter) as a parameter since STORY-406 shipped — but silently never forwarded it into engine_obj.run_output_audit(...). Everything upstream already carried the data the engine needed; the engine just never received it. Fixing that one line, plus giving the engine somewhere to route it, is the whole story. Logged as FND-050 since it's a genuine bug fix, not just new feature wiring.

  • No UI for editing allowlists — configuration only, per Non-Goals.

Understanding check

1. What was the ACTUAL root cause of UC-5 never firing, and why did fixing that one line matter more than the new engine capability?

Reveal answer
services/audit_submission.py's submit_audit_sync already received metadata (with modelId/requestId built by the STORY-406 adapter) as a parameter — it just never forwarded it into engine_obj.run_output_audit(...). The engine could never see envelope data no matter how sophisticated its evaluation logic was, because the data never reached it. Fixing that one dropped kwarg (FND-050) is what actually closes the gap; the new _evaluate_envelope_allowlist logic is meaningless without it.

2. Why does the new "Governance & Compliance" domain never get a `_RISK_SIGNALS` entry?

Reveal answer
It's fed exclusively by envelope evaluation (modelId against an allowlist), never by keyword/regex text scanning. Giving it a `_RISK_SIGNALS` entry would mean ordinary prompt/output text could accidentally trip a "governance" finding, which isn't the intent — this domain represents a structural/configuration violation, not a content risk.

3. Why does `_evaluate_envelope_allowlist`'s result get appended to the SAME `flags` list Gate 3's content scan produces, instead of being recorded through a separate mechanism?

Reveal answer
AC-2.2 requires "TRACE View drill-down parity with content findings" — by joining the same list before _record_gate3_domain_traces/Gate 4/scoring consume it, the envelope finding automatically gets the same AuditTrace shape, the same compliance-mapping attempt, and the same Bayesian/coverage scoring treatment as any content finding, with zero new code in any of those downstream functions.

4. What would happen if an operator's Bedrock log record had a 10KB `modelId` string (malformed or adversarial)?

Reveal answer
Before the security-auditor's fix, it would have been stored verbatim in `AuditTrace.detail_json` — a storage/response-payload bloat risk (not SQL injection or XSS, since the value is ORM-parameterized and React auto-escapes on render). Now `_MAX_ENVELOPE_FIELD_CHARS=256` truncates it before storage, matching the existing `MAX_INLINE_BODY_CHARS` precedent for body text.

5. Why did adding one new MIT domain break two unrelated tests, and was that a bug in this story's implementation?

Reveal answer
Not a bug — a legitimate consequence of the owner's choice (Q1: add a new taxonomy category rather than reuse "AI System Safety"). One test hardcoded "7 domains" as a trace-count assertion; another required every `MIT_DOMAINS` entry to have a `_MIT_DOMAIN_DEFINITIONS` entry (used by the Gate-3 LLM judge prompt). Both were fixed to reflect the new, correct reality (8 domains) rather than weakened or skipped.

6. Two parallel branches (STORY-410 and STORY-411) both created an FND-048. How was that resolved?

Reveal answer
Both branches were created from the same point on `main` (where the highest existing FND was FND-047), and each independently logged its own next-available finding as FND-048 without visibility into the other's in-flight work. STORY-410 merged first (PR #114); at rebase time, STORY-411's finding (ledger row, manifest entry, test filename) was renumbered to FND-050 so both stories' findings coexist without collision.
