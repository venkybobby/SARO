STORY-413 — Dashboard placeholder KPIs: real, hidden, or honestly impossible

Ownership review demo-readiness pack — P0 blocker #3. Pairs with STORY-412.

Context — why this exists

The Dashboard is the demo's opening frame, and the AI Auditor is the deal-killer persona. 8 KPI tiles across the 4 personas (Controls Overdue, Readiness %, Drift Alerts, Rule Pack Version, Coverage Gap %, Failed Scans, Queue Depth, Due This Week) were hardcoded literals captioned "sample — not yet wired to live data." A fabricated compliance number with a fine-print disclaimer is exactly the overclaiming pattern ADR-004 exists to forbid — and it was already flagged and returned in a prior screen review, which is why this story's AC-4 exists: fence it so it can't regenerate.

Intuition

Mental model: a tile now has exactly three states — a real measurement, a loading skeleton, or an explicit "Unavailable." There is no fourth state where a number renders with nothing real behind it.

Quiz

Q1. Why does "Audits (7d)" need its own fetch to /api/v1/audits instead of reusing the audit_count already returned by /api/v1/risk/summary?
audit_count is an unwindowed total (services/risk_service.py: len(audit_records), no date filter) — labeling a total "(7d)" would itself be an ADR-004 overclaim. The /api/v1/audits list endpoint has no server-side date-range param either, so the fix fetches a bounded page (limit=200, the endpoint's max) and counts client-side within a real 7-day window.
Q2. Why was KpiRow exported instead of just tested through the full Dashboard component?
No real persona naturally produces exactly 2 visible tiles post-STORY-413 (ai_auditor=3, the rest=4), and a fetch failure changes a tile's content, not the tile count. Testing the row in isolation with synthetic arrays covers the "2 tiles" case AC-5 asks for without depending on persona-count coincidence.
Q3. What would break if a future PR added a new KPI tile with placeholder: true back into PERSONA_KPIS?
CI would fail on the new "No placeholder KPI tiles on the Dashboard (STORY-413)" step — the regex scan (scripts/check_no_placeholder_kpi_tiles.py) catches the literal placeholder: true text in Dashboard.jsx before it can ship, independent of any component test remembering to check for it.
Q4. Why wasn't "Avg Score" (operator persona) just fixed at the same time, since it's the exact same failure mode?
Its correct meaning was never specified — average risk score per audit? per week? which window? Guessing and shipping a number would risk a different kind of overclaim (a "real-looking" number that doesn't actually mean what its label implies). Logged as FND-052 (status: open) so it's tracked and requires an explicit product decision rather than a silent implementation guess.
