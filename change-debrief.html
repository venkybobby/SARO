Change Debrief — Azure OpenAI + Vertex AI End-to-End Demo Kit

Context — why this exists

Sales and design-partner conversations need a repeatable way to show SARO working against the two cloud AI providers prospects actually run: Azure OpenAI and Vertex AI. The adapters for both have existed since STORY-359/360, and their corpora are byte-verified in CI — but there was no packaged way to walk the pipeline in front of someone, no setup instructions for the customer's cloud side, and no demo video. This change adds all three without modifying a single line of existing pipeline code.

Intuition — the mental model

The demo is a guided replay of what production does. Nothing new is computed; the new runner narrates the existing seam:

What was deliberately NOT done

  • No live Azure/GCP calls anywhere — the demo replays byte-verified corpora; the real-export path is documented, not executed.
  • No new API routes, DB writes, or frontend changes — zero AUDITED/DATA_PLANE surface change.
  • No SDKs added (openai, google-cloud-* remain absent) — INV-1 stays structural.
  • No GIF/MP4 binary committed — the “video” is text-rendered SVG/HTML, regenerable and diffable.
  • No framework-alignment claims in demo materials (EVF status is Internal Review Only — Tier 3).

Quiz — do you actually understand this change?

1. Why does the demo runner never need an Azure or GCP credential?

It replays committed log-export corpora through the adapters. In production the adapters also only read a customer-owned storage export — SARO never calls the provider APIs at all (INV-1/INV-6).

2. What breaks if someone adds a prompt_text field to NormalizedInvocationRecord?

test_contract_has_no_content_bearing_field (STORY-358) fails — and the demo's step 3 would show 16 fields. The body-free property is structural, which is exactly what step 3 demonstrates.

3. Why does Vertex show 66 findings but Azure only 14?

Vertex audit logs never report token counts, so OBS-TOKEN-COUNTS-1 fires per record — at INFO severity because the absence is a provider limitation (field_unavailable), not a customer data gap. Coverage honesty, not extra risk — and a deliberate talking point in Part 4 of the runbook.

4. Why is the tool-scope allowlist supplied by the demo script instead of edited into the pack YAML?

allowed_tools is tenant configuration; with_allowed_tools returns a new pack so tenant policy never mutates shared pack state (INV-3), and the reported hash stays that of the shipped pack.

5. What happens to a malformed corpus line, and why is that the right behavior?

The adapter raises; the runner counts it as "rejected". A half-populated record would be a fabricated observation — worse than a missing one in an evidence system.

6. What breaks if you edit the runner's output text but don't rerun build_demo_screencast.py?

test_committed_screencast_is_in_sync_with_the_demo fails: it re-renders from a live run and byte-compares against the committed SVG/HTML — same discipline as the corpus builders' --check.

7. Why would "SARO found the customer compliant with EU AI Act Art. 9" be forbidden in this demo?

Two independent reasons: SARO never issues compliance verdicts (positioning non-negotiable), and all four frameworks are in Internal Review Only EVF state — Tier 3: no external framework-alignment claims until a QCO exists.

8. On a standard (non-enriched) Azure export, RP-TOOL-SCOPE returns zero findings. Clean result?

No — the standard schema carries no tool data, so there is nothing to evaluate. The capability matrix reports it as "not supported", never as coverage. The demo corpora include enriched records precisely so the rules can be shown firing.
