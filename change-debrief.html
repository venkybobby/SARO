Why this exists

SummitCare's demo needs to run on SARO's real Bedrock ingestion path without touching any client PHI. That requires demo traffic that (a) looks byte-for-byte like a real AWS Bedrock invocation log, (b) is seeded with known findings so every rehearsal is identical, and (c) contains one deliberate blind spot so SARO's coverage-gap attestation has something real to show. This story builds the generator that produces that traffic.

Scope correction made mid-build: the story as written assumed STORY-406 (the Bedrock adapter) and STORY-405 (eval core) didn't exist yet. Recon against current main — not stale memory — found STORY-406 was already built, reviewed, and merged (adapters/bedrock/, 656 lines, its own test suite, PR #112). This story therefore did not rebuild the adapter. It filled the one real gap (an S3-log discovery/reader) and built the generator on top of the real, existing pipeline.

Deviations from a literal reading of the story

STORY-406 was NOT rebuilt. The story spec assumed it didn't exist. Recon found it fully built, reviewed, and merged. Rebuilding would have duplicated 656 lines of already-reviewed, security-hardened code for no benefit.
Gap window reported is wider than the declared 1-hour gap. The manifest declares a missing hour 03:00–04:00; the reconciled gap reports as 02:00–04:00 because heartbeats sit at the top of each hour and gap_start anchors to the last observation before the gap — identical semantics to the existing live detect_gaps(). Not a bug; the test asserts containment, not exact equality.
Coverage stream keyed on a single primary model. STORY-406 keys each coverage stream by full modelId. The manifest pins one primary_model_id so the coverage stream stays continuous and the gap attestation reads as exactly one legible gap.
Mid-review correction: "one checkpoint per hour" was wrong. An early design note claimed the builder guarantees one coverage checkpoint per populated hour. Code review caught that emit_coverage (existing STORY-406 code) actually writes one checkpoint per record — this manifest's 66 records land as 1–2 checkpoints per hour. Correctness was never affected (the gap-detection logic doesn't depend on the false "one per hour" claim), but the design note was corrected, and this surfaced a real, separate bug: no secondary sort key for tied checkpoint timestamps (see Risk map).

  • Did not touch adapters/bedrock/{parse,records,replay}.py or its existing test suite — verified all its existing tests still pass unmodified.

Understanding check

1. Why wasn't the Bedrock adapter (STORY-406) rebuilt as part of this story?

Reveal answer
It was already built, reviewed, and merged on origin/main (PR #112) — 656 lines with its own passing test suite. Recon against current code (not stale session memory) found this. Rebuilding would duplicate already-hardened security controls for zero benefit.

2. Two checkpoints can share the exact same watermark_timestamp in this manifest. Why does that matter, and how was it fixed?

Reveal answer
Without a secondary sort key, which of the tied rows counts as "before" the other is undefined on Postgres (SQLite happened to preserve insertion order, masking the bug in tests). That could non-deterministically flip which watermark_position a gap's boundary records, breaking the byte-for-byte reproducibility this whole story depends on. Fixed by sorting on (watermark_timestamp, watermark_position) — the position is unique per stream, so ties break the same way every time.

3. What's the difference between the two size caps in adapters/bedrock/source.py, and why are both needed?

Reveal answer
MAX_OBJECT_BYTES bounds the compressed bytes read from disk/S3; MAX_DECOMPRESSED_BYTES separately bounds the decompressed output. A small, well-under-the-first-cap gzip object can still expand to gigabytes on decompression (a "decompression bomb") — verified experimentally during security review (150KB compressed → 339MB decompressed). Capping only the compressed size does nothing to stop that.

4. Why is UC-5 (off-allowlist modelId) planted but not asserted as firing?

Reveal answer
The content engine (Gate 3 keyword/regex scan) evaluates prompt+output text — it never looks at the envelope's modelId. Detecting an off-allowlist model requires a rule that doesn't exist yet. UC-5 is included in the corpus for demo completeness but the automated E2E check only asserts on use cases with a real firing rule today.

5. What stops a benign clean-traffic sentence from accidentally becoming a "finding" in the demo?

Reveal answer
_risk_signal_hit() in the builder imports the engine's own _RISK_SIGNALS keyword/regex tables and screens every candidate benign-pool sentence against them before it's used as clean traffic.

6. A malicious log key like "../../../../etc/passwd" is handed to LocalLogStore.read_bytes. What stops it from reading a file outside the demo output directory?

Reveal answer
Two independent checks: the key must match the exact Bedrock layout shape (a regex that a ".." segment cannot satisfy), and separately the resolved path is checked for containment under the store root before any read. Either check alone would likely catch this specific case, but both together are defense-in-depth against a future caller that constructs keys differently.
