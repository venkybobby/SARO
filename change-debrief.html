STORY-TEN-001 — Tenant Isolation: Policies, Proof, Report

Change debrief · story 4/8 · P0 CISO-facing · stacked on story/STORY-CHUB-011

1. Context

RLS was "enabled" on all 47 tables, but that meant nothing: ~35 had zero policies, and RLS is inert at runtime anyway (the service-role pooler bypasses it; nothing sets app.current_tenant). "Enabled ≠ isolated." A CISO doing diligence would find this and walk. TEN-001 makes isolation demonstrated, not asserted: it records the FastAPI-only decision, closes the zero-policy gap, proves isolation with a cross-tenant test suite, and packages it as a diligence report.

2. Intuition — what actually isolates tenants

Under posture (a) FastAPI-only, the enforced control is the API layer: every tenant-scoped query does .filter(Model.tenant_id == current_user.tenant_id). It's fail-closed — an unauthenticated request is 401 before any query, and a user with tenant_id=None filters to zero rows (== None matches nothing), never a leak. RLS is defense-in-depth that only becomes load-bearing under posture (b) direct-DB access (not implemented).

5. Understanding check

Why does adding RLS policies not actually change runtime behavior here?
The app connects via the Supabase service-role pooler, which bypasses RLS, and nothing sets app.current_tenant — so the policies are inert. They close the "zero-policy" inventory gap (AC-1) and become load-bearing only under posture (b). The report discloses this honestly rather than implying RLS is the live control.
Would the test suite catch a developer who forgot the tenant filter on a new endpoint?
For a covered endpoint, yes: test_audits_list_shows_only_own_tenant would fail because TENANT-B's row would appear, and the foreign-id tests would return 200 instead of 404. The residual gap is endpoints not yet in the matrix — which is why the report lists exactly which paths are proven, and the suite is marked to run on every PR touching data access.
A user's tenant_id is None. What does GET /audits return, and why is that safe?
An empty list. The filter Audit.tenant_id == None matches no rows (SQL NULL semantics), so the caller sees nothing rather than everything — fail-closed. The worst case degrades to "no data", never "all tenants' data".
Why is rule_pack_snapshots correctly policy-free while audit_events needed a policy?
rule_pack_snapshots has no tenant_id — published rule-pack versions are global product data, one copy for all tenants, so a tenant policy would be meaningless. audit_events has a tenant_id (it's per-tenant), so leaving it policy-free was a real gap that migration 032 closed.
