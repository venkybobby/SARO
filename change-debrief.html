STORY-MTR-001 — PHI-Free Usage Metering

Change debrief · story 7/8 · commercial foundation P1 · stacked on story/STORY-DISP-001

1. Context

There was no consumption tracking — so pricing had no basis, invoices couldn't be substantiated, and renewal conversations had no delivered-value story. MTR-001 adds per-tenant, per-period usage meters. The hard constraint: metering a healthcare product means it must be PHI-free by construction — a meter must be structurally incapable of holding payload content.

2. Intuition — PHI-free by construction, not by redaction

A meter row is only: tenant, a closed-vocabulary meter key (evaluations_executed, evidence_records_persisted, …), a period bucket, a count, and dimension tags whose keys are a closed set (gate_id, vertical, adapter_id, outcome). There is no free-text column. An unknown meter key or dimension key is rejected at write. So PII can't leak because there's nowhere to put it — redaction isn't even needed.

Metering is best-effort, post-evidence-persist: a metering hiccup logs and continues, never blocking or delaying an evaluation (a dropped increment is acceptable; a blocked healthcare evaluation is not). Loss is bounded and measured by daily reconciliation against authoritative row counts — drift beyond 0.5% raises a data-quality finding.

5. Understanding check

Why is "PHI-free by construction" stronger than redacting PII from meters?
Redaction is a runtime filter that can be forgotten, bypassed, or imperfect. Here the schema has no free-text field at all — meter keys and dimension keys are both closed sets validated at write, and values are bounded tags/counts. There is literally nowhere for payload content to go, so leakage is a structural impossibility, not a policy you have to enforce.
Why is metering best-effort/fail-open when almost everything else in SARO fails closed?
Metering is a commercial/observability concern, not a compliance control. Blocking a healthcare tenant's evaluation because a counter couldn't increment would trade a real safety/availability cost for a billing-accuracy benefit — the wrong trade. A lost increment is acceptable and is caught by reconciliation; a blocked evaluation is not. (Contrast META-001, where privileged WRITES fail closed.)
How does the idempotency key stop double-counting without itself risking cross-tenant issues?
Each logical invocation supplies a unique key (e.g. evidence:{record.id}); if the key was seen, the increment is a no-op. Keys embed a tenant-unique identifier (the record UUID), so the global dedup table can't let one tenant's key suppress another's increment.
What does reconciliation actually compare, and what happens on drift?
It compares the evidence_records_persisted meter total against the authoritative grc_evidence_records row count for the tenant/period. If the relative drift exceeds the configured tolerance (0.5%), it raises a data_quality notification — so lost best-effort increments are bounded and measured, making the "acceptable loss" claim honest rather than hand-wavy.
