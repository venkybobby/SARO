STORY-COV-002 — Live Observation-Checkpoint Emission

Un-deferring COV-001 AC-1 · branch story/STORY-COV-002 · VERIFY debrief

1 · Context — why this exists (plain language)

SARO can now prove how much of the time it was actually watching a client's AI system, and honestly disclose the windows when it wasn't. COV-001 built the machinery (checkpoints → gaps → coverage report, hash-chained, de-identified) but stopped short of the one thing that makes it live: emitting a heartbeat when SARO observes something. That step was deferred on a dependency — STORY-406, a "Bedrock adapter" — that does not exist.

Recon reframed it: SARO is push-model. It never polls a client's model; clients push outputs to be audited. So the real "observation event" is a completed audit. This story wires the existing record_checkpoint() into every live audit path.

2 · Intuition — the mental model

A motion-triggered camera: each audit is a "motion event" that stamps "SARO watched system X at time T." No events for longer than the cadence ⇒ a gap — evidence of SARO's own blind window, not a claim the client was down. Heartbeats are coalesced into time buckets: ≤ one checkpoint per (system, adapter) per bucket.

7 · Understanding check

Q1. Why is a completed audit the right observation event, not a Bedrock adapter?
SARO is push-model and by invariant never polls/calls a client model — it only sees an output when a client submits it. A polling adapter would contradict the read-only, no-external-model posture.
Q2. The reviewer said "bound detect_gaps to a recency window." Why did we NOT do exactly that?
A stale system's latest checkpoint is by definition old, so a recency filter would exclude the very keys that should open a gap — silently breaking detection. The correct fix is a DB-side GROUP BY max(timestamp) that reduces cost without dropping stale keys.
Q3. Two audits for claude land in the same 60s bucket concurrently. What happens to the loser?
It hits the UNIQUE constraint at autoflush/commit; record_checkpoint catches IntegrityError, rolls back, returns None (idempotent no-op). Before the fix it left the session in PendingRollbackError, silently killing the downstream SAR-008 notification. (FND-047)
Q4. A tenant submits nothing for a day, then pulls a coverage report. What does it show?
observation_events: 0, coverage_attested: false, and a caveat that coverage_pct is vacuous. The raw 100% is still shown but explicitly marked un-attested — honesty in the examiner-facing artifact, which is the whole point of the story.
Q5. Why must bucket_seconds stay below the cadence?
Within one bucket only the first audit records a heartbeat. If the bucket exceeds the cadence, an actively-observed system could look stale between heartbeats and get a false gap. 60 < 300 keeps a live window always leaving a heartbeat.
Q6. Emission raises mid-audit. What does the client see?
Nothing — the audit completes normally. Every call site swallows emission errors (fail-open), matching DISP/MTR; the audit record is already committed before emission. Proven by test_grc_path_is_fail_open_on_emit_error.
