# STORY-408 — Cross-Account Client Log Pull

**Status:** Specced, **PILOT-GATED — do not build until SummitCare pilot is signed.** The client-facing onboarding one-pager (FR-4) is the exception: produce it now for the pilot conversation.
**Depends on:** STORY-406/407 (S3LogStore, source reader); STORY-410 (CLI surface)
**Delivery rule:** Integrated into the single SARO repo.

## Problem Statement

The pull pipeline authenticates only with SARO's own ambient AWS credentials. Real clients' Bedrock invocation logs live in the client's S3 bucket, in the client's account, typically SSE-KMS encrypted. Clients will not push logs (correct assumption — pull is the architecture and the pitch). SARO must assume a client-provisioned, read-only, least-privilege IAM role to pull, and the client must be able to set that up in minutes from an artifact we hand them.

## Goals

1. `S3LogStore` can operate under an assumed cross-account role with automatic credential refresh.
2. Per-tenant source configuration binds a tenant to exactly one client log source with its auth parameters.
3. A client runs one template and one page of instructions to grant access — the "10 minutes on your side" demo claim becomes literally true.
4. Confused-deputy and privilege-scope risks are tested, not just documented.

## Non-Goals

- No client-side agents, no push/webhook ingestion, no CloudWatch Logs path (still P2).
- No multi-source-per-tenant fan-in (P2).
- No secrets for long-lived client credentials — role assumption only; SARO never stores client access keys.

## Functional Requirements

### FR-1: Per-tenant source config (P0)
Config record per tenant: `role_arn`, `external_id`, `bucket`, `prefix`, `region`, expected `kms_key_arn` (informational), enabled flag.

**AC-1.1:** Config is validated at load (ARN shapes, region format, prefix normalization) at the boundary, same discipline as STORY-407's manifest validation.
**AC-1.2:** `external_id` is generated by SARO per tenant (cryptographically random, ≥ 32 chars), stored server-side, displayed once during onboarding artifact generation, never logged.

### FR-2: Role assumption in S3LogStore (P0)
**AC-2.1:** Given a tenant source config, `S3LogStore` obtains credentials via STS `AssumeRole` with the tenant's `external_id`, and all discovery/read calls use those credentials — never SARO's ambient credentials against a client bucket.
**AC-2.2:** Credentials auto-refresh for runs longer than the session lifetime (use botocore's refreshable-credentials mechanism or re-assume per batch — pick least-code option, document it). A test simulates expiry mid-run and asserts completion.
**AC-2.3:** SSE-KMS objects decrypt transparently when the assumed role has `kms:Decrypt`; a missing-KMS-permission failure produces a distinct, actionable error message naming the key requirement (this will be the #1 client setup mistake).
**AC-2.4:** Existing local/own-account paths continue to work unchanged (demo path must not regress).

### FR-3: Security properties (P0)
**AC-3.1:** Confused-deputy test: assuming the role without the correct `external_id` fails (integration test against a test role, or a contract test on the AssumeRole call parameters if live AWS testing is out of CI scope — flag which).
**AC-3.2:** The reader never attempts writes; a test asserts no PutObject/Delete calls are possible through the store interface (interface-level guarantee, not just "we don't currently call it").
**AC-3.3:** Read scope is prefix-bound: keys outside the configured prefix are never requested (extends STORY-407's key-shape validation to the cross-account path).
**AC-3.4:** No client data or credentials in logs: assumed-role session tokens, external IDs, and object bodies never appear in SARO log output (test greps structured logs from a full run).
**AC-3.5:** security-auditor review required before merge (this story is the pilot's security review surface).

### FR-4: Client onboarding artifact (P0 — BUILD NOW, ahead of the code)
A CloudFormation template (and/or Terraform equivalent — ask which SummitCare prefers) creating:
- IAM role with trust policy: principal = SARO's account, condition `sts:ExternalId` = tenant's external id.
- Permissions: `s3:ListBucket` (prefix-conditioned) + `s3:GetObject` on `arn:aws:s3:::<bucket>/<prefix>*` + `kms:Decrypt` on the client's log KMS key. Nothing else. No wildcards on resources.
- Plus a one-page setup doc: enable Bedrock model invocation logging to S3 (console steps + the `put-model-invocation-logging-configuration` CLI alternative), run the template, send SARO the role ARN. Written for a client cloud engineer, reviewed against ADR-004 (no capability overclaims).

**AC-4.1:** Template deploys clean in a fresh test account; SARO can pull with the resulting role; removing the ExternalId condition or narrowing the prefix behaves as expected.
**AC-4.2:** The doc's step count and time estimate are validated by actually performing it once, timed.

### FR-5: CLI integration (P1)
**AC-5.1:** `saro ingest --tenant <t>` resolves the tenant's source config automatically; `--source` override retained for demo/local use.
